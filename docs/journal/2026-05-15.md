## What's NOT done, ranked

1. **No SQLite for non-wallet state.** Wallet users re-derive cleanly via SIWE. But `allowedToStream` toggles and the seeded admin's stream key vanish on restart. Cost of this bug grows with every feature added that depends on per-user persistent state. ~2-3 sessions if done right (schema + migrations + repo pattern).

2. **No frontend tests.** Mocking the wagmi/wallet/SIWE/viem stack is genuinely painful — that's why I deferred. The right move is probably Playwright e2e against a running stack, not Vitest unit tests with mocks. Half-session of investigation followed by a session of writing the actual flow tests.

3. **Docker deploy is unverified.** Files are structurally correct based on Docker idioms I know, but `docker build` has never run against this Dockerfile on this machine. Likely failure modes: (a) bcrypt native compile in Alpine needing extra deps, (b) ffmpeg-static binary not finding its libstdc++ companion despite the libc6-compat install. Fast to debug once Docker is in hand.

4. **Recording lifecycle still polls.** `donePublish` event → 30s poll for the mp4 file to finalize → move + upload. If ffmpeg dies mid-record, the file never appears and the recording is silently lost. Should be `fs.watch` + a retry queue persisted to SQLite (so see #1).

5. **Frontend bundle is 1.7MB ungzipped.** No code-splitting. The wallet stack accounts for most of it. Vite supports `manualChunks` for easy splitting; do it once when ready to ship to mobile users.

6. **The PowerShell launchers (`*.ps1`) are still in the repo** alongside the cross-platform npm scripts. They'll drift over time. Easy to delete once a Windows user confirms `npm run dev` works for them.

## Likely-surprising context

- The remote is `https://github.com/idl3o/live-video-player.git`. The user's "main" branch is `dummy-deployment` — that's not a typo and it's the canonical target for PRs. Recent commit history before this sprint was single-number commit messages like `1151`, `853`, `852` — informal repo, but the new PRs use real descriptive messages and the user has accepted that pace.

- `--legacy-peer-deps` is needed for npm installs across the board because RainbowKit v2 declares a `wagmi@^2.9.0` peer range that doesn't match the latest wagmi point releases. The CI workflow already passes the flag; remember to use it locally too.

- The blockchain workspace is **ethers v6**, but the backend workspace still has `ethers@^5.7.2` in package.json (was there before the sprint, never used in the new code). It's harmless but worth removing on a cleanup pass.

- `@storacha/client` is the actively-maintained fork after web3.storage rebranded. Its subpath exports (`@storacha/client/principal/ed25519`, `@storacha/client/proof`) don't resolve under the backend's CommonJS-flavored TypeScript moduleResolution; I use dynamic imports cast through `any` as a deliberate technical-debt note. Long-term fix is `moduleResolution: "node16"` in [backend/tsconfig.json](../../backend/tsconfig.json) but that touches every file's import order.

- Two TypeScript files have intentional `any` casts wired to runtime libraries that don't ship clean types: [IPFSService.ts](../../backend/src/services/IPFSService.ts) (Storacha subpath imports) and the wagmi event-log args in [RecentTips.tsx](../../frontend/src/components/RecentTips.tsx). Both fully tested at runtime.

- The "low-latency (FLV)" checkbox in the viewer pane is real. iPhone users will land on the HLS path automatically. Desktop users can opt into FLV for sub-2s latency.

- Each Web3 feature is independently env-gated. The product gracefully degrades when env vars are missing — components either hide themselves or render a "set X to enable" notice. So the user can deploy a partial stack and add primitives one at a time. Don't be surprised if you see no payment-stream UI on a fresh deploy; check `VITE_PAYMENT_SUPER_TOKEN`.
